# ADR 0052: Support for hosting partners: confidential tenants, pseudonymised telemetry, usage

- **Status:** Proposed (pilot built); §7 replaced by [ADR 0053](0053-support-connections-and-support-requests.md)
- **Date:** 2026-11-07
- **Deciders:** Epistola team
- **Tags:** support, telemetry, privacy, usage, billing, saas
- **Related:** [ADR 0050](0050-support-connection.md) (the support connection),
  [ADR 0051](0051-catalog-mirror.md) (the catalog mirror),
  [`docs/support-protocol.md`](../support-protocol.md) (the wire protocol, v1)

## Context

ADR 0050 connects an installation to Epistola support, and the installation is the unit: one
registration, one contact, one set of granted services. That fits a customer who runs the suite for
itself. It fits less well a **hosting partner**: one installation, run by the partner, with a tenant
per client of that partner.

- **The partner is Epistola's customer; its clients are confidential by default.** Epistola must not
  learn who they are from what the installation sends. Tenant keys usually name the client.
- **Telemetry is installation-wide** and log lines carry free text, the tenant key and stack traces.
  Some partners agree to ship everything; others require pseudonymisation at least.
- **A partner may be bound not to share** a client's data at all, while a tenant admin can opt in to
  feedback or the mirror today; the installation preset is only a default.
- **Partners bill by use**, and Epistola bills the partner: the number of generated documents has to
  reach Epistola reliably, which best-effort telemetry does not.
- **Partners run their own support desk.** Feedback going straight to Epistola bypasses it.
- Log lines carry **no trace or span id** today (Micrometer Tracing is not on the runtime classpath),
  so neither the suite's own log nor telemetry can follow one request.

## Decision

### 1. Tenant identity: named or confidential

An installation setting says what Epistola sees of its tenants. **Confidential is the default.**

- **Named**: tenant keys are sent as they are.
- **Confidential**: every tenant is sent as a **tenant reference**, `t-` and a hex HMAC-SHA-256 of
  the tenant key under a secret generated by the installation that never leaves it. A plain hash
  would not do: tenant keys are guessable. The same reference is used everywhere (telemetry,
  feedback, usage), so Epistola can correlate one tenant's errors and use without knowing who it is.
  The platform page shows each tenant's reference, so the partner can tell Epistola who it is when it
  wants to.

The **catalog mirror is unavailable in confidential mode**: a release archive holds the templates
themselves, which name the client whatever key it is filed under.

### 2. Telemetry: everything or pseudonymised

A second installation setting. **Pseudonymised** means:

- **Logs**: the message as written in the code (the logging pattern, `"Render failed for {}"`),
  without the arguments; an exception as its type and stack frames, without its message; trace and
  span id; logger name; the tenant as its reference. Thread names and every other log-context value
  are dropped. Only the suite's own loggers are forwarded below WARN, since some libraries format
  values into the message themselves.
- **Metrics**: a `tenant` tag carries the tenant reference; a `template` tag is dropped.
- **A guard** forbids string templates in log messages in suite code, so the pattern carries no
  values.

**Everything** sends what the suite sends today, with the tenant as named or referenced per §1.

### 3. Every request has a trace

A `ScopedValue` holds the current trace and span id, in W3C Trace Context form. A servlet filter
starts a trace per request and continues an incoming `traceparent`; every command and query dispatch
is a child span; work handed to another thread through the mediator context carries it. The ids are
mirrored into the logging context (`traceId`, `spanId`), so the console log, the database log and
telemetry all carry them. Full OpenTelemetry tracing stays possible later; the ids are compatible.

### 4. The installation id is checked, not only stamped

The suite always sends `epistola.installation.id` as a resource attribute. The support service
rejects a telemetry request whose resources lack it or carry another one than the token's (`400
installation_mismatch`), counts the rejection and shows it on the registration. It still stamps the
token's identity, and strips the identity keys at every level (scope, log record, data point), not
only the resource. Epistola's collector accepts traffic only from the support service.

### 5. Four settings for every shared service

The installation setting of a shared service is one of:

| Setting         | The tenant                                  |
| --------------- | ------------------------------------------- |
| Required        | cannot change it                            |
| On by default   | follows it, or opts out                     |
| Off by default  | follows it, or opts in                      |
| Not allowed     | cannot opt in; sees why and who decides     |
| Ask each tenant | decides when it sets up support (no preset) |

A service offers the settings that make sense for it. **Feedback and the mirror do not offer
Required**: anything that sends tenant content needs the tenant's opt-in (ADR 0050 §10), and a
default is not that. **Usage offers Required, On, Off and Not allowed**, and its tenant page does not
show it while it is Required. In confidential mode the mirror offers only Not allowed.

### 6. Usage for billing

A service of its own, scope `usage`, separate from telemetry: telemetry is lossy and switchable, a
bill is neither.

- The suite keeps **generation statistics** in core, per tenant: documents generated and failed, and
  previews rendered, per UTC hour for a week (`epistola.statistics.hourly-retention`), then per day,
  kept. Generation does no extra work for them: a background roll-up on one node reads each
  `generation_results` row once, after its position, and adds it up; deleting a document does not touch
  its result, so it still counts. Previews are counted in memory and written once a minute per node.
  The statistics lag the results by minutes, then agree with them. Tenants see them on their Generation
  page; usage reporting is one reader of them.
- Partition maintenance records every partition it drops (table, month, estimated rows, size) in
  `partition_history`, from the catalog, so months can be compared after their rows are gone.
- Every finished hour is reported once the statistics hold all of it, at a moment within the first ten
  minutes past the hour, chosen at random per installation and kept, with a **meter reading** per sharing tenant: its figures for the hour and its
  running totals: `PUT /api/v1/usage/hours/{hour}`. Hourly, so a silent installation shows within
  hours, not a day.
- The service bills from the totals (what they grew by since the tenant's previous reading), so a lost
  report loses nothing. A tenant's first reading, its first after missing from a report (it stopped
  sharing) and totals that went down (a restored database) bill nothing and are flagged. The hourly
  figures cross-check the totals.
- The backoffice shows totals per month with missing hours, the last report, silent installations
  (three hours without a report) and the flags, and exports a CSV per installation and tenant.

The count is self-reported, as any self-hosted licence is; where telemetry is shared, its generation
metrics can cross-check it.

### 7. Feedback connectors (replaced by ADR 0053)

> Replaced by [ADR 0053](0053-support-connections-and-support-requests.md): support connections in
> the plural, and escalation between them from the suite. Kept as written.

Feedback goes to one or more **connectors** set up at platform level: Epistola support (all feedback,
or only what partner staff escalate) and a partner's own desk (CloudEvents over signed webhooks, with
replies through the REST API). One connector owns the status; comments from all are shown with their
source. Without an enabled connector, the feedback form says that feedback stays in the installation.
Not built in this round. What feedback needs from its host is kept to a short contract
([`docs/support-requests.md`](../support-requests.md#the-host-contract)): W3C trace ids in pages and answers, the
console and trace buffers, `FeedbackLogSource` for a request's server log, `FeedbackSyncPort` for
where feedback goes, so it can later move to another application or out on its own.

## Consequences

- A partner can connect without disclosing its clients, and choose per installation how much
  telemetry carries.
- The tenant reference is stable for as long as the installation secret is; losing the secret (a new
  installation) starts new references.
- Log lines can be followed per request, in the suite's own log too.
- An installation id mismatch is visible instead of silently corrected.
- Usage becomes a reliable number Epistola can bill on.

### Deferred

- Feedback connectors (§7).
- Per-client services and pauses: services stay per installation.
