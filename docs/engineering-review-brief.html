Epistola Suite — engineering review brief

What the system is, how it is built, what enforces quality, and — deliberately up front — what is still wrong with it. Every claim here is traceable to a path in the repository.

02 What it is

A multi-tenant document generation platform. Business users design templates in a block editor; developers generate PDFs through a REST API. The unit of work is a template, which owns a JSON-Schema data contract and N variants (language, brand, audience), each with immutable numbered versions that move DRAFT → PUBLISHED → ARCHIVED and are promoted per environment. Templates, themes, stencils, fonts, code lists and attributes are all owned by a catalog, which is the unit of exchange between installations.

Rendering is direct to iText — a normalised flat node/slot graph straight to PDF, with no intermediate HTML and no headless browser. 10–50 ms simple, 50–200 ms complex.

03 The dispatch path — where the guarantees live

This is the part worth defending in detail. Authorization is not sprinkled across controllers; it is a property of the message, checked centrally, and fail-closed by construction.

Multi-tenancy, honestly stated

Isolation is application-level, not database-level. There is no row-level security and no schema-per-tenant. Three layers carry it instead:

  • A TENANT_KEY domain type and a tenant_key column with a cascading FK on every tenant-owned table; composite FKs thread (tenant, catalog, template, variant, version) through the whole graph.
  • TenantScoped / RequiresPermission.tenantKey checked at the mediator against tenant_memberships.
  • Every handler's SQL filters on tenant_key, helped by TenantQueries extension functions that bake the scoping in.

Expect this to be challenged. The honest answer is in §07.

04 Module structure and the commercial boundary

05 How Epistola and GZAC integrate

GZAC (Generiek Zaakafhandelcomponent) is Valtimo-based, so Epistola plugs in as a Valtimo plugin rather than as a bespoke integration: app.epistola.valtimo:epistola-plugin on Maven Central for the backend and @epistola.app/valtimo-plugin on npm for the Angular side, EUPL-1.2, currently targeting the Valtimo 13.x line. It registers through Valtimo's public extension points only — PLUGINS_TOKEN, MenuService.registerAppendMenuItemsFunction() and registerCustomFormioComponent() — so it adds a plugin, a menu entry and Form.io components without forking or patching the host.

Why a feed rather than a callback or a timer loop

The naive BPMN pattern is a timer loop — generate, wait 30 s, poll, repeat — which makes the process engine wake every waiting instance just to ask "done yet?". The plugin replaces that with a message intermediate catch event fed by one collector per plugin configuration. Webhooks were the other option and were not taken: a callback needs Epistola to reach into the municipal network, needs retry and dead-letter handling on the sending side, and breaks the moment GZAC is behind a firewall. A pull feed inverts all three — GZAC dials out, and its cursor is the only delivery state that matters.

The war story worth telling. The feed is Kafka-shaped: monotonic sequence, consumer-held cursor. A destructive database reset in a test environment restarted the BIGSERIAL at 1 while the consumer's cursor survived at 4 — so every new result landed below the cursor and was silently never delivered. Valtimo catch events simply never fired. The fix seeds the sequence from wall-clock epoch-milliseconds on every schema (re)initialisation, so any post-reset sequence strictly exceeds every previously issued one and a stale cursor always self-heals — no client change, and deploying it unblocks an already-stuck consumer on next boot. It is a good illustration of the failure mode this architecture actually has: not crashes, but silence.

What a reviewer will probe here

  • Multiple Valtimo instances against one tenant. Handled: results are spread over 64 routing partitions assigned to consumer nodes through a consistent-hash ring, with submitting-node affinity so the instance that submitted a job tends to receive its own result. There is an integration test named for exactly that (SubmittingNodeAffinityIT).
  • Delivery semantics. At-least-once, deliberately — the suite's stated stance is that work must never be permanently orphaned, and it prefers a duplicate over a loss. Correlation is keyed on jobPath, and the collector resumes from its cursor after a crash.
  • Authentication is the weak spot, and it is the same one as finding #5. Today each API key is implicitly a consumer — its UUID lands in consumer_node_assignments when a Valtimo node first polls — and an API key carries every tenant role. The epistola-contract spec already defines a full Consumer Management surface (register, approve/reject, per-resource permissions, public keys, node visibility) and the suite has not implemented any of it. That is the cleanest example of the broad-API-key finding having a real, customer-visible consequence rather than a theoretical one.
  • Latency. Peers pick up work on a ~5 s poll, so a small batch drains on the submitting node; LISTEN/NOTIFY is the intended fix and is not built.

06 What actually enforces quality

The strongest claim available: conventions here are build failures, not wiki pages. Eighteen architecture tests run in the fast unitTest cycle with no Spring and no Docker, scanning the whole repo from settings.gradle.kts.

Guard Fails the build when…
AuthorizationCoverageTest any command or query does not declare an Authorized contract
MediatorWiringTest a message has zero or two handlers, or a handler is not a @Component — otherwise a runtime-only failure on first dispatch
DomainBoundaryTest a handler is imported outside its own package, i.e. someone bypassed the mediator and with it authz, metrics and events
ApplicationClockUsageTest production code calls Instant.now() and friends instead of EpistolaClock. The allowlist is currently empty
UiRestApiSeparationTest a template or static JS file calls the versioned REST API
CspTemplateComplianceTest an inline <script>, an on*= handler or an hx-on::* attribute appears — all silently dead under the strict CSP
UiTestHygieneTest a Playwright test uses waitForTimeout, :visible or a blind waitForSelector — a deliberate anti-flake ratchet, no test retries anywhere
NoHardcodedSecretsTest a committed config file holds a literal secret rather than ${ENV} — complements gitleaks rather than duplicating it
IconUsageTest · PageHeaderUsageTest a template references a missing icon, or misspells a fragment parameter — Thymeleaf silently nulls typos
MovableResourceGuardTest a resource type resolved by address at render time is registered as movable — which would break every published template using it
checkMigrationVersions a new migration sorts before the target branch head, or an already-merged migration is edited, renamed or deleted
checkContractVersionAlignment the backend, the editor package and the pnpm lockfile disagree on the contract version
BundledCatalogFingerprintTest bundled catalog content changed without a regenerated fingerprint

Pipeline and supply chain

  • CI — one build job packages the Gradle build cache as an artifact so the two test jobs run from cache; UI tests get a dedicated runner because CPU contention was the root cause of the historic flake (issue #418).
  • Security — CodeQL (Kotlin + TS, security-and-quality suite, weekly and per-PR), gitleaks over full history, daily Trivy scan on both SBOMs with SARIF into Code Scanning and an auto-filed deduplicated issue, Trivy config scan on the Helm charts. Any CRITICAL fails the build.
  • Release — tag must match gradle.properties; a -SNAPSHOT cannot ship; image is cosign-signed and the CycloneDX SBOM cosign-attested.
  • Dependencies — Renovate with a 7-day minimum release age (mirrored in pnpm-workspace.yaml, with an explicit postinstall allowlist); minor and patch auto-merge, majors and the whole toolchain never do.
  • Two failure modes only reproduce outside JUnit, so they are scripted rather than pretended away: scripts/multi-instance-test.sh (3 nodes, SIGKILL chaos, stale-job recovery) and scripts/deadlock-burst-test.sh (the fat-jar nested-classloader deadlock that needs a cold concurrent first-load burst — the reason rendering runs on platform threads, not virtual ones).

08 Questions they are likely to ask

Application-level tenant isolation — why no row-level security?

Straight answer: because the mediator gate plus FK-carried tenant keys covers it, and RLS would add a second, partly-overlapping enforcement model without removing the first. The cost is that a handler which forgets its WHERE tenant_key is a data leak that no compiler catches. The mitigations are TenantQueries helpers, dedicated tenant-isolation tests, and DomainBoundaryTest forcing everything through the gate. If a reviewer pushes for RLS as defence in depth, that is a fair hit — take it as a to-do rather than defending the gap.

Why a hand-rolled mediator instead of Axon, or Spring Modulith?

The mediator is roughly 12 small files. What it buys is one place where authorization, transaction propagation, metrics, audit and the event log attach to every domain operation — and that is exactly why all three surfaces stay thin. It is CQRS as a dispatch convention, not event sourcing: there is no aggregate rehydration, no snapshotting, no separate read model. Adopting a framework would have imported all of that vocabulary for the one property actually wanted. Spring Modulith is the one genuinely worth revisiting — it targets precisely finding #1.

JDBI and hand-written SQL rather than JPA?

Deliberate. The schema is heavily composite-keyed, partitioned by month, and uses FOR UPDATE SKIP LOCKED for job claiming — all things an ORM obscures or fights. The price is paid honestly: SQL is spread across handlers, and the internal to-do list already carries "niet zo blij met al die SQL overal". Custom argument factories and column mappers keep typed keys and encrypted credentials from being stringly-typed at the boundary.

Server-rendered Thymeleaf + HTMX in 2026 — really?

Yes, and it is the reason a two-person-scale team ships this surface area. There is exactly one place where rich client state genuinely pays: the template editor, which is Lit + ProseMirror. Everything else is a form or a list. The corroborating detail is the CSP: script-src 'self' with no inline script anywhere, which is only affordable because there is no SPA build smuggling inline bootstrapping into the page.

What is the bus factor?

Low — and do not dress it up. What compensates is that the knowledge is externalised rather than resident: 115 docs, 16 ADRs, a self-critical architecture review, 18 machine-enforced conventions, and a CLAUDE.md that encodes the working rules an onboarding engineer would otherwise have to absorb by osmosis. The correct framing is that the conventions survive the author, because they fail the build rather than a code review.

Can we trust an upgrade not to eat our data?

From RC1 onward the database is stable and never reset. Migrations are forward-only and module-owned; checkMigrationVersions rejects any edit to an already-merged migration. Deployment defaults to a migration job (Helm pre-upgrade hook) with app pods in validate mode — they fail fast if the schema is behind and never migrate at boot — and a separate DDL-capable role is supported so the runtime role has no DDL at all. Downgrades are explicitly unsupported; rollback is restore-from-backup. Two most recent minor lines are supported.

What breaks if we never pay you?

Nothing that is running. The whole repository is AGPL-3.0 and the support tier is enabled=false by default — the JARs ship but construct no beans. Feedback, quality checks and backups all work locally; what the tier adds is sync to the separate hub server, plus an SLA. The one honest caveat: version-check phones home once a day with the running version and a stable installation id, on by default, disabled with a single property.

Show me evidence it survives horizontal scaling.

A real 3-node test on 10 July 2026 found three bugs (#723, #724, #725), all fixed, and the harness that found them is committed. The stance is stated explicitly as at-least-once over at-most-once: work must never be permanently orphaned. Defences are layered — scheduler-liveness election on last_poll_completed_at rather than heartbeat alone (a wedged poll thread keeps heartbeating and would otherwise starve the whole fleet), a 15-minute hard-deadline watchdog, and per-node document recovery. Known gap: peers only pick up work on a ~5 s poll, so a small batch drains on the submitting node. LISTEN/NOTIFY is the intended fix and is not built.

Coverage is 79% — is that gated?

No. The badge is informational; there is no Kover verification rule. Defensible position: the guard tests and 994 real-database integration tests are the actual gate, and a coverage threshold mostly buys test-shaped code. But it is a fair criticism, and "we measure it and chose not to gate it" is the only honest version of the answer.

If you had three months, what would you fix?

In order: (1) scoped API keys and MCP opt-in — the two combine into the largest real exposure; (2) an enforced timeout on JavaScript expression evaluation; (3) allowlisting file: and outbound URL fetching; (4) narrowing SystemInternal into context-bound markers; (5) explicit module activation so a dependency cannot silently add routes, schedulers and migrations. That is the review's own priority order, unchanged.
