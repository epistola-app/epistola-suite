# Epistola 2.0 — progress

What we touched, how each change is covered, and what we noticed but left alone, so that at any
moment we can see where 2.0 stands and check that nothing is uncovered.

The design lives in the contract repo (`epistola-contract`, branch `feature/v2`, ADRs
`docs/adr/0001`–`0005`). The suite plan is `docs/catalog-release-model-v2.md`, still to be rewritten
against those ADRs.

**Coverage legend:** ✅ test exists and was run green · 🟡 test exists, not run since the change ·
❌ no test · ➖ no test needed (docs, deletion, merge).

## Current state (16 October 2026)

- `release/2.0` = main up to v1.5.0 + #1003, #1056, #1057, #1060, #1061, #1088. Version
  `1.5.1-SNAPSHOT`.

  repository, not on Sonatype snapshots.

  pushed): catching up with the contract snapshot of 16 October.

## Design: catalogs by opaque id, named by registry + namespace + key — decided 16 October

User: a key is not unique per tenant (two `letters` in different namespaces must coexist), and
correctness beats effort. Resources already have opaque ids (`catalog_resources.resource_id`) and
reference each other by them; catalogs get the same treatment.

Schema (verified against the migrated schema, not the migration files):

- `catalogs`: new opaque `catalog_id UUID` (UUIDv7), primary key `(tenant_key, catalog_id)`; column
  `id` renamed `catalog_key`; identity `UNIQUE (tenant_key, registry, namespace, catalog_key)`.
- **Live tables reference the catalog by `catalog_id`** (FK to `catalogs`, `ON DELETE CASCADE` as
  today), replacing `catalog_key`: `catalog_resources`, `themes`, `document_templates`,
  `variant_attribute_definitions`, `assets`, `stencils`, `code_lists`, `fonts` (address
  `UNIQUE (tenant_key, catalog_id, key)`); `catalog_releases` (PK `(tenant_key, catalog_id,
  version)`) and its dependants `release_entries`, `catalog_release_publications`,
  `environment_catalog_deployments`; `catalog_upstream_checks`.
- **History keeps the name it had:** `documents` and `document_generation_requests` (partitioned)
  and `environment_deployment_log` keep `catalog_key` and gain `registry` and `namespace`,

## Design: stencils by reference (step 2) — decided 16 October

Recorded as **contract ADR 0006** (`epistola-contract` `docs/adr/0006-stencil-instances-by-reference.md`,
commit `9ff4d72` on `feature/v2`, local), status Proposed: parts 1–4 decided, part 5 (isolation) proposed.

Today (mapped 16 October): a stencil instance is an **embedded copy** in the template's stencil node
(`children` slot), with props `stencilId`, `catalogKey`, `version`, `draftVersion`,
`parameterSchemaSnapshot`, `parameterBindings`; placeholder fills live in the copy's `fill` slots.
The renderer only reads the copy (`StencilNodeRenderer`), never the stencil. Upgrading an instance
is `UpdateStencilInTemplate` + `StencilContentReplacer`, which reports `droppedFills`,
`droppedBindings`, `unboundRequired` but blocks on none.

**Decided (16 October, user): no copy.** A template stores an instance as a reference (stencil key,
catalog when not its own), its bindings, and one placeholder node per placeholder it fills. The
stencil is resolved when the template is opened, previewed or rendered — in the same catalog
version, or in the pinned release of a dependency. A stencil change reaches every template at once;
releasing checks every instance against its stencil (unknown fill or unbound required parameter =
error, unknown binding = warning), like a compile step. No digests, no held back, no propagation.
Stencils in stencils work the same way (inner references resolve in the stencil's catalog; the outer
stencil fills the inner one's placeholders and can pass its own placeholders through); the suite
still refuses nested stencils (`rejectUnsupportedNestedStencilAuthoring`); **decided 16 October: stencils in stencils must be possible** — remove the refusal and verify the editor in the wiring step.

**Fill scope: lexical (decided 16 October, user).** A fill sees what was in scope where it was
written; a stencil's interface is exactly its placeholders and parameters.

Upgrade from 1.x must not change what renders (user requirement). Plan, not built (ADR 0006 table):
no expression rewriting. Where 1.x fills read the instance's alias, the stencil's placeholder gets
`passParameters` (and a non-default alias goes onto the fill as `parametersAs`); where 1.x stencil
content reads template data, the stencil gets `readsTemplateData`. Detection parses expressions
(JSONata AST). A 1.x readiness check counts both.

**Placeholder passes parameters (decided 16 October, user):** opt-in per placeholder by the stencil
author; the name is chosen by the using side, defaulting to the author's, else `params`.

**Decided 16 October (user):**

- 1.x instances on an older stencil version are **upgraded automatically** to the latest stencil
  (they render the latest after the upgrade). What no longer fits (dropped fills, unbound required
  parameters — the `StencilInstances` findings) is **reported**: upgrade report and quality findings.
- Copies that are not a normal locked copy (no `stencilId`, or content differing from the pinned
  version beyond fills) become plain content and are reported — collapsing them would lose content.
- A release preview of templates affected by a stencil change comes **later**; prepare for it by
  keeping "templates affected by a stencil change" a query of its own.

**Superseded proposal** (copies + held back; kept for the record):

- A stencil has one working copy (content + parameter schema) and a ready mark; `stencil_versions` goes.
- An instance keeps its embedded copy and loses `version`/`draftVersion`.
- **Marking a stencil ready moves every instance in the same catalog** whose template it does not
  break (`StencilContentReplacer`; breaking = it would drop a fill or binding, or leave a newly
  required parameter unbound). Breaking instances are **held back** on their old copy, listed in
  stencil usage, and block the release until the variant is edited.
- Cross-catalog instances move when the dependency pin moves (to confirm).
- Upgrade from 1.x: the first release is cut from today's copies (renders exactly as before); then
  instances behind the latest stencil are moved in the draft, breaking ones held back.

Goes with it (step 2 scope): `stencil_versions` and its commands (`CreateStencilVersion`,
`UpdateStencilDraft`, `PublishStencilVersion`, `ArchiveStencilVersion`), `PublishVersion`'s
published-stencil check, the interim `stencilVersionPinFindings`, `MultipleStencilVersionsInUseException`

- `FindStencilVersionExportConflicts`, `OnStencilConflict` and the renumber plumbing, the usage
  page's `UpgradeBlockReason`, the client-side bulk upgrade (`stencil-detail.js`), MCP
  `list_stencil_versions`/`get_stencil_version`/`update_stencil_draft`, editor `draft-hydration.ts`
  and `upgrade-refs.ts`, REST's draft/publish-based stencil working copy.

Decided (16 October, user):

- An instance stores a **content digest** and an **interface digest** (placeholders + parameter
  schema). Different content digest = behind. Same interface digest = safe to move. Different
  interface digest = check the instance (does it use a removed or retyped fill or binding, or leave
  a newly required parameter unbound) — only then held back.
- Cross-catalog instances move when the dependency pin moves, "like upgrading a Java library":
  preview the breaking instances before moving the pin; breaking ones are held back and block the
  release.
- While template versions still exist, a stencil update writes into template drafts.

Proposed, awaiting the user — what the template author sees on stencil ready:
A silent update · B update and reset templates to modified · C mark stale, update on request ·
**D (recommended)**: compatible copies move, template keeps its ready mark with a non-blocking
"updated by stencil X" note in history and release changes; breaking ones held back; the stencil
author sees a preview ("updates 37 templates, 2 held back") when marking ready. C fits only if
template and stencil owners must not change each other's work.

## Design: catalog versions (step 4, ADR 0002) — proposed 17 October, not built

The contract addresses every resource as `…/catalogs/{registry}/{namespace}/{key}/versions/{v}/…`:
reads on any version, writes and ready marks on drafts only (`409` on a released one). Several
drafts may be open; a draft is an independent copy with a fixed base, can be `behind`, is renumbered
with acknowledged warnings, and releasing it is a state change of the same version. Dependencies
are per version (`…/versions/{v}/dependencies`).

**Identity across versions, content per draft.** `catalog_resources.resource_id` stays the one
identity of a resource in every version (the quality ledger, generation history, relocation and
release entries already key on it). What a draft holds is stored per draft:

- New `catalog_versions (tenant_key, version_id UUID, catalog_id, version, status draft|released,
  base_version, source_version, released_at…)`; `UNIQUE (catalog_id, version)`. A released version
  keeps its row; its content is the retained release content (`release_entries`), so its live rows
  are dropped on release and reads of it go through `ReleaseContentAssembler`.
- Every live content table keys on `(tenant_key, version_id, resource_id)` instead of
  `(tenant_key, resource_id)`, and its address `UNIQUE (version_id, key)`. References between
  content rows (a template's theme, variants of a template) carry `version_id` in their FKs, so a
  reference always resolves in the same draft.
- `catalogAt(t, c)` (175 SQL sites) splits into `catalogAt` (catalog-level tables: releases,
  deployments, upstream checks) and `draftAt(t, c, v)` (content). `CatalogId` gains an optional
  version; without one, a write resolves to the catalog's only open draft and is refused when there
  are several (so callers that do not know about versions keep working while one draft is open).
- Creating a draft copies the content rows of its source (a draft's live rows, or a released
  version's retained content) under the new `version_id`, keeping every `resource_id`.
- Subscribed catalogs have no drafts: their installed release is their content (one implicit
  version row, read-only).
- `catalog_dependencies` moves to the version (declarations are per draft, as the contract says).

**First, remove template and contract versions (4a).** With catalog versions, `template_versions`
(draft/published per variant) and `contract_versions` are a second, conflicting version axis. A
variant holds one model per draft, a template one data contract per draft; publishing becomes the
per-resource ready mark (`markTemplateReady`, `markVariantReady`, `markStencilReady`), a stored
digest cleared by an edit. Upgrade rule (plan): the last published template version becomes the
first release's content; an open draft becomes the open draft's content; older versions are lost.

**4a in detail (decided 17 October; contract `markVariantReady`/`markTemplateReady`/
`markStencilReady`/`markCatalogReady`/`getCatalogChanges` are the authority — the ready mark stays,
`docs/v2-simplify-first` is superseded on this point):**

- Storage: `template_variants.template_model` (+ `referenced_paths`), `document_templates.data_model`
  and `data_examples`. Backfill: the open draft, else the latest published version (same for the
  contract). `template_versions`/`contract_versions` stay as unread history (data is never dropped);
  the pre-2.0 generation path for already-queued requests keeps reading them.
- Ready: `resource_ready_marks (tenant_key, resource_id, part, digest)`; `part` is the variant key for
  a template (a variant's readiness includes the template's shared fields and data contract, as the
  contract says), `''` otherwise. The digest is computed **in SQL** by one view,
  `resource_content_digests`, over the stored content of every resource type, so a mark is a copy of
  the view's value, an edit invalidates it without bookkeeping, and the upgrade backfills it in SQL.
- Changed vs base stays `GetCatalogResourceChanges` (canonical per-resource fingerprints against the
  base release); a release is refused while a changed resource is not ready.
- Upgrade semantics: a variant with no open draft is marked ready (its published content was
  releasable before); a variant with an open draft is not (its draft was not). Same for contracts.
- Names: `UpdateVariantContent`, `MarkVariantReady`, `MarkTemplateReady`, `MarkStencilReady`,
  `MarkCatalogReady`, `UpdateDataContract`; the version commands and queries go.

**Alternatives rejected:** a draft as its own `catalogs` row (releases and deployments are per
catalog, so they would need a second id anyway); one live working copy with other drafts as stored
snapshots checked out on edit (writes to two drafts at once would swap content back and forth);
one open draft at a time (correct but not ADR 0002).

## Design: several drafts (step 4b) — decided 17 October, deferred (see Plan)

Refines the step 4 design above against the schema as it is after 4a (dumped from a migrated
scratch database, 17 October).

1. **`catalog_versions` replaces `catalog_drafts`** (that migration is not in `main`, so it is
   rewritten): `(tenant_key, version_id UUID, catalog_id, version, kind draft|installed,
   base_version, created_from, created_at)`, PK `(tenant_key, version_id)`, `UNIQUE (tenant_key,
   catalog_id, version)`. An authored catalog has one row per open draft; a subscribed catalog one
   `installed` row, read-only, numbered by its installed release. A released version has no row:
   its content is the retained release content, read through `ReleaseContentAssembler`. A number is
   unique across drafts and releases (checked by the commands, as renumber already does).
2. **Content rows belong to a version.** `themes`, `document_templates`, `template_variants`,
   `variant_attribute_definitions`, `code_lists`, `code_list_entries`, `assets`, `fonts`,
   `font_variants`, `stencils` drop `catalog_id` and gain `version_id`: PK `(tenant_key, version_id,
   resource_id)` (children: plus their own key), address `UNIQUE (tenant_key, version_id, key)`.
   `catalog_id` is dropped rather than kept so every SQL site not yet converted fails loudly instead
   of returning one row per draft.
3. **Identity stays per catalog.** `catalog_resources (tenant_key, resource_id, catalog_id, type,
   key)` is unchanged: one resource has one identity in every version and every release (quality,
   generation history, relocation and release entries key on it).
4. **References name identities, never rows.** FKs that pointed at a content row's
   `(tenant_key, resource_id)` point at `catalog_resources` instead: a template's theme, an
   attribute's code list, a font face's asset, the tenant's default theme, and the history and
   feature tables (`quality_findings`, `quality_finding_ignores`, `load_test_runs`,
   `template_versions`, `contract_versions`, `stencil_versions`, `environment_activations`). A
   reference resolves in the version being read when it is in the same catalog, and in the
   dependency's locked release when it is in another (ADR 0003) — as rendering already does.
5. **Per-version state:** `resource_ready_marks` and `catalog_dependencies` gain `version_id`; the
   `resource_content_digests` view carries it.
6. **SQL:** `catalogAt(t, c)` stays for catalog-level tables (releases, deployments, upstream
   checks, identity). Content uses `versionAt(t, c)`: the catalog's only content version (its one
   draft, or its installed row), and is refused when there are several, so a caller that does not
   name a version keeps working while one draft is open. Callers that name one use
   `versionNamed(t, c, v)`. `CatalogId` stays as it is; a version-aware id is added where the
   contract's `…/versions/{v}` reaches a command.
7. **Lifecycle:** creating a draft copies the content rows of its source (another draft, or a
   released version's retained content) under a new `version_id`, keeping every `resource_id` and
   asset binary. Releasing a draft records the release and, when no draft above it exists, renumbers
   that same version row to the next patch (the content rows stay put, as one draft works today);
   otherwise its rows are deleted. Deleting a draft deletes its rows.
8. **Slices:** (a) schema + backfill (every existing catalog's rows to its one version) + helpers,
   behaviour unchanged with one draft; (b) convert every SQL site, guarded by the full suite;
   (c) create, delete, `behind`, release with several drafts, renumber over several; (d) REST
   `createCatalogVersion`/`deleteCatalogVersion` and version-scoped writes, MCP, UI.
