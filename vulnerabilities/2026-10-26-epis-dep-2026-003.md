# Brotli decoder out-of-bounds write (CVE-2026-111497)

CVE-2026-111497 is an out-of-bounds write in Google's C Brotli decoder, versions 1.0.3 through
1.2.0 (fixed in 1.0.10, 1.1.1 and 1.2.1, upstream commit `0ed4268`). An invalid block switch is
reported as "needs more input" instead of a format error, and the streaming decoder keeps
appending input to an eight-byte internal buffer. Node.js bundles the decoder, which is how most
reports reach it, but anything that feeds untrusted Brotli data to the C library is exposed.

**Epistola Suite is not affected.** The image does contain the vulnerable library, so a scanner
reporting it is correct about presence. No untrusted input can reach it.

## What is in the image

Checked against the published `ghcr.io/epistola-app/epistola-suite:1.5.0` image (amd64):

| Component                                            | Present                                                                                                                                       |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Node.js                                              | **No.** No `node` binary anywhere in the image. Node is a build tool here; the editor ships as static JS.                                     |
| `libbrotli1` 1.1.0-2build2                           | **Yes**, pulled in by `libfreetype6`, which `fontconfig` needs. The run-image Dockerfile installs both.                                       |
| Liberica JRE's `libfontmanager.so`                   | Links the JRE's **own** `libfreetype.so`, which does not link Brotli. No JRE library links `libbrotli*`.                                      |
| `brotli4j` / `org.brotli:dec`                        | **No**, in neither `apps/epistola` nor `apps/pdfrender`.                                                                                      |
| Netty, HttpClient 5, Commons Compress Brotli classes | Present but inert: each needs `brotli4j` or `org.brotli:dec` at runtime, and neither is there.                                                |
| iText `com.itextpdf.io.codec.brotli`                 | A pure-Java decoder (used for WOFF2 and the PDF `BrotliDecode` filter). Not the affected C code, and the JVM bounds-checks every array write. |

## Why no attacker input reaches the C decoder

`libbrotlidec` is called only by the system FreeType, and the system FreeType is used only by
fontconfig, to index the fonts baked into the image under `/usr/share/fonts` (root-owned). The
JVM's font rendering uses its bundled FreeType instead. Uploaded fonts never touch either: they
are parsed by iText in Java.

On the HTTP side, the suite runs on embedded Tomcat, which compresses responses but does not
decompress request bodies, so `Content-Encoding: br` on a request is not decoded at all. The
HTTP clients the suite uses do not advertise or decode Brotli without the missing libraries.

## What we will do

Ship a rebuilt image once Ubuntu publishes a patched `libbrotli1` for 24.04. No fix had been
published on 26 October 2026.

Releases up to and including 1.5.0 built on `paketobuildpacks/run-noble-base`, which Paketo
stopped updating in April 2024, so they could not have picked up an Ubuntu fix at all. The run
image now builds on the maintained `paketobuildpacks/ubuntu-noble-run`, so the first release
built after Ubuntu ships the fix carries it.

No mitigation is needed in the meantime. Rejecting `Content-Encoding: br` at the ingress is
harmless if an operator wants to anyway, but it changes nothing for the suite.
