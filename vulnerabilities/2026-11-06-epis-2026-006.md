# Tenant administrators can create API keys with roles they do not hold

Creating an API key requires the tenant administrator's permission. The roles the key authenticates
as were chosen freely: neither the create dialog nor the `CreateApiKey` command checked that they
were among the creator's own. Roles are composable and do not inherit, and the separation between
administering a tenant and publishing its content is documented as deliberate.

## Impact

A tenant administrator who holds no content roles could create a key with the publisher, author,
generator or viewer role, and with it, through the REST API or MCP: release catalogs and deploy
releases to any environment, production included (on 1.x: publish template and stencil versions);
publish releases to a release registry, which cannot be taken back; edit content; generate
documents; and read generated documents. The separation of duties between administration and
publishing was therefore not enforced.

Installations where every administrator also holds every content role are not affected in
practice.

## Severity

This vulnerability is rated **Medium**, CVSS 3.1 score **6.5**
(`CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:N`). The administrator/publisher split is a boundary
the product documents. Confidentiality is high because a key may read generated documents with
personal data in them; integrity is high because releases and deployments decide which documents are
produced.

## Affected versions

From 0.18.0 (`399a53c97681aead66c4da0b362d28057a87eb93`), which added key creation to the UI: every
key then carried every role. 0.25.0 scoped keys to chosen roles, but did not limit the choice to the
creator's. Every release from 0.18.0 through 1.5.0 is affected, and the 2.0 pre-releases
2.0.0-alpha.1 and 2.0.0-beta.1.

## Resolution

Fixed in **1.5.1** (`fad4e5900fb3460461f8179d8f5370e5569dc228`) and on the 2.0 line in
`44ffa8470cf589d430a08ef7138ce61dae3f7394`, which ships in the next 2.0 pre-release.

Creating a key refuses any role its creator does not hold in that tenant, counting tenant and global
roles together, in the `CreateApiKey` command that every surface goes through. The create dialog
offers only those roles. Keys created before the fix keep their roles.

Upgrade to 1.5.1, then review existing keys at `/tenants/{tenant}/api-keys` for roles wider than
their creator's. If you cannot upgrade yet, grant the administrator role only to people trusted with
every content role.
