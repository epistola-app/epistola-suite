# SVG assets make the PDF renderer fetch external resources and read local image files

Image assets may be SVG files, and the PDF renderer converts them with iText's SVG module. It did
so with iText's default settings, which resolve the resources an SVG refers to against the working
directory and load them over any URL scheme. Nothing inspected an SVG's content when it was stored:
the web UI, the REST API, the MCP tools and catalog import all accepted any SVG.

## Impact

An authenticated user with permission to edit templates in a tenant could upload an SVG image whose
`<image href>` or `xlink:href`, `<link rel="stylesheet">`, `xml-stylesheet` instruction, CSS
`@import` or `@font-face` source points at a URL. Every preview or generated document that showed
the image made the renderer — the application server or a render worker — request that URL, so it
could probe or reach hosts on the internal network that the user cannot reach themselves. A
`file:` URL or absolute path to an image file on the server embedded that local image in the PDF,
which the user could then read back. Only files the image decoder accepts are disclosed; XML
external entities and external DTDs were not resolved. Responses to network requests are not
returned unless they are images.

## Severity

This vulnerability is rated **Medium**, CVSS 3.1 score **5.0**
(`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:L/I:N/A:N`). It is reachable over the network by any user
who holds the low-privileged template-edit permission in a tenant and needs no user interaction.
Scope is changed because the requests and file reads are made by the server against systems and
files outside the suite's own authorization. Confidentiality impact is low: disclosure is limited
to image files and to what can be learned from server-side requests.

## Resolution

Every SVG is now converted through one place that refuses all external resources: the resource
retriever returns nothing for any URL, the base URI is a fixed unresolvable placeholder, SVG text
uses the standard PDF fonts only, and CSS `@import` rules — which iText fetches with its own
retriever — are removed before conversion. Inline base64 `data:` images, `#fragment` references,
shapes and text still render. This also covers SVGs stored by an affected release, so no data
migration is needed; an SVG that referenced something external renders without it.

As defence in depth, every write path now refuses an SVG with a DOCTYPE, scripts, `foreignObject`,
event-handler attributes, `href`s other than `#fragment` or `data:`, `xml-stylesheet`
instructions, or CSS with `@import`, escapes or a `url()` to anything else. Served SVG assets carry
`X-Content-Type-Options: nosniff` and a sandboxing `Content-Security-Policy`.

Fixed in **1.4.0** (`1ef2a161ebb3dfec82d5933e1bdc087487a34aec`),
released on 13 October 2026. Every later release carries the fix, the 2.0 line included.

Upgrade to 1.4.0 or later. Where that cannot happen at once, restrict the template-edit
permission to trusted users and restrict outbound network access from application servers and
render workers.
