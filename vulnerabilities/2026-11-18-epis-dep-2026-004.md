# Java4Shell: heap overwrite in the JRE's Base64 decoder (CVE-2026-114938)

CVE-2026-114938 ("Java4Shell", disclosed 17 November 2026) is a memory-corruption bug in
OpenJDK's x86-64 Base64 intrinsic, the hand-written AVX-512 VBMI routine that the C2 compiler uses
for `java.util.Base64` decoding. A padded tail such as 64 × `A` followed by `=` makes the routine
compute a negative output length and write a full 64-byte vector, up to 62 bytes past the end of
the output array. The researchers turned the overwrite into a heap disclosure and remote code
execution in several products. OpenJDK fixed it in 17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1.

**Epistola Suite is affected** on x86-64 hosts whose CPU has AVX-512 VBMI: Intel Xeon Ice Lake and
newer, AMD Zen 4 and newer, which covers most current cloud machines. ARM64 hosts are not affected.
On Linux, the host is affected when all four flags print:

```bash
grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'
```

## How an attacker reaches it

Every image up to and including 2.0.0 and 1.5.1 ships Liberica JRE 25.0.5.0.3+5. Spring Session's
`DefaultCookieSerializer` Base64-decodes the `sid` session cookie on every request to the web UI,
before authentication, through `java.util.Base64`. An unauthenticated client can therefore send
valid cookies until the decoder is compiled, and then a malformed one. Turning the overwrite into
code execution needs an exploit tailored to the application, but the heap corruption alone is
reachable without credentials.

Other decoding in the suite (MCP uploads, support assets, credential envelopes) needs a signed-in
user. JWTs are parsed by Nimbus, which has its own Base64 decoder.

## Mitigation and fix

Epistola 2.0.1 and 1.5.2 start the JVM with `-XX:-UseBASE64Intrinsics`, which replaces the affected
routine with the pure-Java decoder. The flag is appended at start-up, so a `JAVA_TOOL_OPTIONS` set by
the deployment keeps it, and the image build fails when it is missing. Base64 behaves the same,
only slower on large payloads (about 1.5 ms per 2 MB).

On an older image, set `-XX:-UseBASE64Intrinsics` in `JAVA_TOOL_OPTIONS`; in the Helm chart that is
`jvm.options`, whose default carries the flag from the next chart release on. The flag is accepted
on ARM64 too. Do not use the alternative `-XX:UseAVX=2`: the JVM refuses it on ARM64 and it slows
down far more than Base64.

The fix itself is Liberica JRE 25.0.5.1, which reached the images with Paketo builder 0.0.222.
Epistola 2.1.0 ships it and no longer sets the flag (pull request #1459). The 1.x line keeps the
mitigation: its 1.5.x images still ship 25.0.5.0.3 with the flag.

## Why our scans did not report it

Trivy does not detect a JRE that a buildpack installs as a layer: it is not an operating-system
package and not a jar. Paketo records it only in the image's own buildpack SBOM
(`/layers/sbom/launch/paketo-buildpacks_bellsoft-liberica/jre/sbom.syft.json`), as
`pkg:generic/bellsoft-jre@25.0.5` with the CPE `cpe:2.3:a:oracle:jre:25.0.5`, which Trivy does not
read. The backend SBOM lists the dependencies of the application, not the runtime under it. A
maintainer reported this vulnerability the morning after disclosure.

The daily CVE watch now also checks the runtime of every supported image against the OpenJDK
vulnerability advisories (`scripts/cve_watch.py runtime-scan`, see `docs/sbom.md`). Run against
2.0.0 and 1.5.1, it reports this CVE and four more HIGH ones from the same advisory
(CVE-2026-114939 to CVE-2026-114942), which the watch files as their own issues.
