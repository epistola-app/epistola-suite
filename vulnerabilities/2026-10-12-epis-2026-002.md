# Authenticated local file read and server-side request forgery through catalog and code-list source URLs

A catalog subscription and a URL-sourced code list are both a URL the server fetches. The URL a
user entered was checked only for a `.json` suffix, an allowed scheme (`https:`, `file:`,
`classpath:`, and `http:` where enabled) and a literal `..`; nothing restricted which host, address
or directory it reached. The URLs a fetched manifest named for its resource details and binaries
were not checked at all.

## Impact

A user allowed to manage catalogs could subscribe to a manifest that names an image or font binary
at a `file:` URL or an internal address. Installing the catalog stored those bytes as a tenant
asset, which could then be downloaded: an arbitrary file readable by the server process (for
example `/proc/self/environ`) or the response of an internal service, including a cloud metadata
endpoint. The HTTP client also followed redirects without re-checking them and read responses of
any size. A user allowed to edit code lists could make the server request internal addresses and
`.json` files, and a failed refresh stored the raw error, including fragments of the response, in a
field shown in the UI.

## Severity

This vulnerability is rated **Medium**, CVSS 3.1 score **6.8**
(`CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:N/A:N`). The scored path is the catalog one: it requires
the catalog-management permission and reads files and internal services outside the application's
own authority. The code-list path needs a lower permission but returns less.

## Resolution

Every catalog and code-list read now goes through one guard. `file:` sources are off unless
`epistola.catalog.file-roots` names directories, and then only reach files whose canonical path is
inside one. `classpath:` reads only Epistola's own bundled catalogs. Network sources must resolve to public
addresses only, checked at the connection itself so a changing DNS answer cannot bypass it; an
intranet installation can allow private addresses with
`epistola.catalog.outbound.allow-private-networks` or `allowed-hosts`, while link-local addresses
stay refused. A manifest may name its details and binaries only by a path relative to, and below, its own location, so it can reach neither another host nor another scheme, and a catalog's credentials never leave the manifest's origin. Redirects are followed by hand and
re-checked, credentials are dropped across origins, responses are capped, and a failed code-list
refresh stores a generic message.

Until a patched release is available, operators can limit the catalog-management and code-list
editing permissions to trusted administrators and restrict the server's outbound network access.
Once the fix is released, this record must be updated with the first patched version, the fixed
commit and the publication date.
