# Unbounded JavaScript expression evaluation allows render-worker denial of service

Template expressions carry a language. Besides JSONata and simple paths, the template model
accepts `javascript`, which the suite evaluated with an embedded GraalJS engine. The engine was
sandboxed against host, file, network, process and thread access, but enforced no limit on
statements, running time or memory. The editor only ever writes JSONata expressions, but a template
or stencil with a JavaScript expression could be stored through the REST API, a catalog or ZIP
import, or the MCP authoring tools.

## Impact

An authenticated user with permission to edit templates in any tenant could store an expression
such as an endless loop and then preview or generate a document from it. Evaluation would occupy a
render thread indefinitely and could exhaust memory. Render workers drain a queue shared by all
tenants, so a few such requests could stop document generation for every tenant of an installation.
No confidentiality or integrity impact is known.

## Severity

This vulnerability is rated **Medium**, CVSS 3.1 score **6.5**
(`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H`). It is reachable over the network by any user who
holds the low-privileged template-edit permission in a tenant, needs no user interaction, and
results in a complete loss of document-generation availability. Scope is scored as unchanged: the
affected component is the suite itself, even though the denial of service crosses tenant
boundaries within it.

## Resolution

The JavaScript engine and its GraalVM polyglot dependencies are removed. Every write path —
editor saves, the REST API, catalog and ZIP import, and MCP authoring — now rejects a template or
stencil containing a JavaScript expression, and a template stored by an affected release fails to
render with a clear error instead of being evaluated. This is a deliberate breaking change to a
feature that was never offered in the editor. No stored data is changed; the generation guide
documents a query that lists template and stencil versions still holding such an expression, so
operators can rewrite them in JSONata.

Fixed in **1.4.0** (`2c3e084dc7e65a8a0121754d8506c4abcdffe944`),
released on 13 October 2026. Every later release carries the fix, the 2.0 line included.

Upgrade to 1.4.0 or later, and use the query in the generation guide to find and rewrite any
JavaScript expression still stored. Where upgrading cannot happen at once, restrict the
template-edit permission to trusted users.
