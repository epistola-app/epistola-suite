# Apache Tomcat container-managed security bypasses (CVE-2026-65182, CVE-2026-65905, CVE-2026-68525)

Trivy failed the `main` build on three CRITICAL findings against
`org.apache.tomcat.embed:tomcat-embed-core` 11.0.24, the version managed by the Spring Boot
4.1.1 BOM.

**Epistola Suite is not affected.** All three vulnerabilities live in Tomcat's
container-managed servlet security — the `web.xml` world — and the suite uses none of it.
The embedded Tomcat serves requests; it makes no authorization decisions.

## The findings

| CVE            | Upstream summary                                   | Apache severity | Preconditions                                                                                            |
| -------------- | -------------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------------- |
| CVE-2026-65182 | Security-constraint bypass                         | Important       | A `web.xml` constraint for a longer path declared _before_ a more restrictive one for a shorter sub-path |
| CVE-2026-65905 | Limited replay in the DIGEST authenticator         | Low             | DIGEST authentication configured, and a `nonceCount` on the upper boundary of the replay window          |
| CVE-2026-68525 | FORM-authentication redirect bypasses a constraint | Low             | FORM authentication configured, plus a constraint limiting a resource by POST but not GET                |

Note the severity mismatch: Apache rates two of the three **Low** and none of them Critical.
The CI gate fires on Trivy's CRITICAL label alone and has no way to express that.

## Why the vulnerable code is not in our execute path

Every filter chain in
[`SecurityConfig.kt`](../apps/epistola/src/main/kotlin/app/epistola/suite/config/SecurityConfig.kt)
is Spring Security: an API-key filter, an OAuth2 resource server (JWT), OIDC login, and
Spring Security's `formLogin`.

That last one deserves care, because the name collides with the vulnerability. Spring
Security's form login is `UsernamePasswordAuthenticationFilter` — an ordinary servlet filter
in the Spring chain. Tomcat's `org.apache.catalina.authenticator.FormAuthenticator` is a
container component activated by a `<login-config auth-method="FORM">` declaration in
`web.xml`. CVE-2026-68525 concerns the latter. We use the former, and configure the latter
nowhere.

Evidence, searched across the whole tree excluding build output:

- no `web.xml` of any kind;
- no `login-config`, `auth-method`, `SecurityConstraint` or `SecurityCollection`;
- no `DigestAuthenticator` or `FormAuthenticator`;
- no `Valve`, `TomcatContextCustomizer`, `TomcatServletWebServerFactory` or
  `@ServletComponentScan` — nothing reconfigures the container's security layer.

Because the classes are present in the jar but never reached, the OpenVEX justification is
`vulnerable_code_not_in_execute_path` rather than `vulnerable_code_not_present`.

## What we did

Upgraded anyway. 11.0.25 fixes all three and is a drop-in, so `apps/epistola` and
`apps/pdfrender` both moved their `extra["tomcat.version"]` override to it. Non-exploitability
is an argument you have to keep making; a version bump ends it. The recorded assessment stands
for the version we shipped with and for anyone scanning an older artifact of ours.

Verified with the same Trivy 0.74 scan CI runs: zero findings at CRITICAL **and** HIGH.

## A second problem this exposed

The override that preceded this one pinned 11.0.22 while the Spring Boot BOM had already
moved to 11.0.24 — so a pin written to _raise_ the version had silently become a
**downgrade**, and its comment still cited Spring Boot 4.0.6 and two long-superseded CVEs
(see [EPIS-DEP-2026-002](2026-05-20-epis-dep-2026-002.md)). Both comments now name the
current BOM version and the condition for removing the pin.

This is the argument for keeping these records at all: an override outlives the reason for
it, and without a written reason nobody can tell a security floor from an accidental ceiling.
