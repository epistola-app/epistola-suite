title: Templates are no longer versioned; you work in a catalog's next version and publish it, numbered from what changed.
---

In 1.x every template, data contract and stencil had versions of its own, published one at a time. In 2.0 the catalog version is the only version. A template variant has one model and a template one data contract, both edited in place, and everyday work goes into the catalog's **next version**, which has no number until you publish it. **Publish…**, offered on every page of the catalog, lists what changes by name ("Added: Invoice (Template)") and says what that means for whoever uses the catalog: only corrections, additions that keep everything working, or a warning naming what can break. It picks the number from that — corrections raise the patch, additions the minor, breaking changes the major — and you may raise it under Advanced, never lower it; a catalog's first version is 1.0.0. After publishing, the next version carries on from what was published, and discarding it throws its changes away and starts it again from the latest published version. A large change that is not ready goes into **long-term work**: a named copy started from the next version or a published version and kept apart from everyday work. You try it on a test environment, and when it is ready, **Make this the next version** turns it into the next version, after you confirm each version published since it started; the old next version is kept under a name or discarded. Long-term work itself is never published. Behind publishing is a **ready mark**: a record that a resource's current content is reviewed, which any edit makes stale. Publishing in the web UI marks the changes ready for you; over REST and MCP you mark a variant, template, stencil or the whole catalog ready, and releasing is refused while a change is not ready. Marking a variant ready runs the checks that publishing a template version used to.
