---
type: feat
scopes: [catalog, mcp, api]
audience: user
title: A draft can take in a release it is behind, resource by resource (alpha).
---

A draft that is behind a release, such as the next version after a fix was released from other work or a release received from another installation, can now merge it instead of only acknowledging it. The merge takes what only the release changed, keeps what only the draft changed, and asks for a choice where both changed the same resource. A release that removes something the draft still uses is refused. Available in the web UI from the draft's page and the catalog's page, over MCP as `preview_merge` and `merge_release`, and over REST as `previewCatalogDraftMerge` (`GET …/releases/{draft}/merge-preview?version=`) and `mergeIntoCatalogDraft` (`POST …/releases/{draft}/merge`), with the problem types `merge-conflicts-unresolved`, `merge-refused` and `merge-not-applicable`. The catalog's default theme, presets and dependency declarations merge the same way, each as one entry. A merge confirmed against a preview that is out of date, because the draft or the release changed since, is refused and asks to preview again (MCP: `preview_merge` returns a `token` that `merge_release` takes; REST: the preview's `token`, sent as `expectedToken`, refused with `merge-preview-outdated`). Merging within one resource is not supported yet.

The merge compares against the release both the draft and the release come from, found by the base each release names (catalog archives now carry it), never guessed from the release numbers. When this installation does not have that release, the preview says which one to get first (from a registry, the Exchange or a file) and the merge is refused (REST `missingBase` and `merge-base-missing`); when no release both come from is known, every difference is a choice. Resources are compared by their complete fingerprint, so a change to only a template's description or a variant's metadata counts as a change.

A release remembers the releases that were merged into it before it was released, and says so in its archive (`release.metadata`, `app.epistola.suite.merged`), so an installation receiving it and a tenant snapshot keep them. A draft is now behind exactly the releases numbered below its next number that its line does not contain, its base and what was merged into it or into the releases it came from: a fix released long before the next release last moved on is listed until it is merged, and a fix merged before a release is never listed again after it. The web UI says for each release a draft lacks which release it was made on and when it was published; when a draft lacks several, the catalog's page and the draft's page show them as one group with their count and a small drawing of the releases the draft continues from, with each missing release branching off the release it was made on.

Each catalog a version uses is now an entry of its own in a merge, `catalogDependency/<catalogKey>`, valued by its declaration (the release it pins, or the draft it names), in place of the single `catalog/dependencies` entry: a release that adds or re-pins one catalog and a draft that changes another merge without a conflict; only both sides changing the same catalog differently asks for a choice.

A merge is refused when its result would hold a reference that does not resolve: within the catalog, into a catalog the result does not declare, or into the release a declaration pins that lacks it (the pinned release is checked, not that catalog's next release). The refusal says what is missing and what to choose instead, such as "the default theme 'brand' of 'shared' needs 'shared' as a dependency: take v1.0.1's dependency on 'shared' too, or keep your default theme". The preview names, for each entry, the entries it goes with (a template's theme, the dependency a reference resolves through): the web UI shows "Goes with …", MCP `preview_merge` and REST `previewCatalogDraftMerge` return `needs`. Setting a catalog's default theme to a theme of a pinned dependency now checks that the pinned release has it.

A conflict can also be resolved with merged content, combining both sides instead of choosing one: read the entry on its three sides (as it was when both started, as the draft has it, as the release has it) in the portable catalog format, combine them, and merge the result. Over MCP `get_merge_sides` reads the sides and `merge_release` takes `mergedContent`; its descriptions guide an assistant to propose the combined content and merge only once the user agrees. Over REST `getCatalogDraftMergeSides` (`GET …/releases/{draft}/merge-sides?version=&entry=`) reads them and `mergeIntoCatalogDraft` takes `mergedContent` and returns `merged`. Merged content is validated as an import validates content (400 `validation-error`, the field naming `mergedContent.<type/key>` and the path within it), checked like every merge (409 `merge-refused`), and written as given but not marked ready, so it is reviewed before the draft is released. The draft's page and the publish dialog mark each such resource "Merged, review before publishing" until every part of it is marked ready (publishing marks it), and the publish dialog names them ("These were merged, review them: …"); MCP `get_catalog_changes` returns `mergedForReview`. The web UI's merge dialog can show a conflict's three sides side by side ("Compare") and still resolves it to one side. A path or query parameter that breaks the REST contract's constraints is now 400 `validation-error` instead of 500.
