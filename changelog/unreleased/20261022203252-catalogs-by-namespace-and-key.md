title: Catalogs are addressed by namespace and key, and two with one key can live side by side as an alpha feature.
---

Within a tenant a catalog is named by namespace and key. Two catalogs with one key (`acme/letters` and `bureau/letters`) are an alpha feature, **Catalogs sharing a key** (`shared-catalog-keys`), off by default: without it a second catalog with a key the tenant already uses is refused, whether it is created, imported or installed. Tenant snapshots, background checks and some pages do not tell two such catalogs apart yet. A catalog's pages are at `/tenants/{tenant}/catalogs/{namespace}/{key}/…`; an address by key alone still opens the one catalog with that key, and is refused, naming the catalogs, when the key names several. Over MCP a tool's `catalogId` may be written `namespace/key` (`list_catalogs` gives each catalog's `address`). With the feature on, a catalog received from another namespace is installed beside one of the tenant's own with the same key. Every page listing a tenant's catalogs (the home page, the catalog list, the dependency and resource graphs, the catalog switcher, an environment, generation history) shows the two as two entries, each linked by its namespace, and a page reached by namespace links its catalog the same way. REST `listCatalogs` and MCP `list_catalogs` give each its own editability, REST environment deployments name each by its own catalog, and MCP `apply_house_theme` names the catalogs it changed by `address` (`namespace/key`) instead of by key.
