title: A catalog installs and upgrades as one unit.
---

Installing a subscribed catalog took an optional list of resources, and an upgrade then preserved whatever subset you had chosen, topping it up only with resources you ticked individually. That made "installed 1.2.0" mean something different on every installation: the version and fingerprint on the catalog row are the publisher's statement about a whole release, and a local subset is not that release. It also made every rule built on top conditional on what the installer happened to pick — whether a cross-catalog dependency is satisfied, what an upgrade diff is comparing, which resources a catalog-wide action covers. Installing now installs the whole manifest, and an upgrade reconciles it: resources added since the installed release arrive, changed ones are updated, and ones the publisher withdrew are removed under the existing in-use conflict checks. The per-resource Install button and the "also install new resources" checkbox are gone. The upgrade preview keeps its job and does it better: it now names what is new, what is updated and what is removed, rather than naming only the last two and counting the first. It is the last point at which someone can see that a resource they rely on is about to disappear, or that content they have never reviewed is about to arrive. A publisher who wants parts adopted independently publishes more than one catalog. An installation left partial by the old behaviour is topped up by its next install or upgrade, and the upgrade preview shows those additions first. The REST upgrade request still accepts `includeNewSlugs` and now ignores it — the surface is GA, and a full upgrade is a superset of anything that field could ask for. A catalog can no longer end up partial by accident either: installing from a URL fetched and wrote one resource at a time, so a resource that failed left everything before it installed and reported a failure count. It now fetches the whole catalog first and writes it in one transaction, so a failure leaves nothing behind — the guarantee the ZIP import has always given. Holding a catalog in memory to do that is bounded by the same `epistola.catalog.max-decompressed-size` limit a ZIP import already respects, so a catalog too large to import as an archive is not accepted as a source instead.
