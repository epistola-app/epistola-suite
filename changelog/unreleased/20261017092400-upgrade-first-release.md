title: The upgrade from 1.x gives every catalog a first published version, and deploys nothing.
---

Upgrading from 1.x is a breaking upgrade that needs a maintenance window, and document generation stops at the upgrade until you deploy (follow the Upgrades guide). Before upgrading, take a database-level backup and drain the generation queue, and plan to move REST clients to contract 2.0. On upgrade each template variant and stencil keeps what you were working on (its draft, else its latest published version), and what was published counts as ready, so unfinished 1.x drafts are what remains to publish. The 1.x template, data contract and stencil versions and the environment activations are removed once the upgrade has taken what it needs; a summary of them (version numbers, statuses, dates, and what each environment had activated) is kept as the `upgrade-1x-history` record in `app_metadata`, and the content of older versions is not kept. 1.x environments activated template versions and no 1.x release kept its content, so as soon as the application starts a background task prepares every catalog that existed before the upgrade: an authored catalog gets a dependency on each catalog its content uses and a first published version made from what was last published before 2.0, numbered as the next patch after its latest 1.x release, or 1.0.0. The 1.x releases themselves are removed, since they kept only a number, a fingerprint and notes, and their Exchange publication records with them, so each catalog starts with that one release and its next version on top. A template whose default variant was never published, and a stencil never published, are left out of it, and unpublished work stays in the next version. A subscribed catalog gets the release it has installed recorded as one it can render from. A catalog that cannot be prepared yet, for instance because a catalog it uses has no release yet, is retried every five minutes with the reason logged. The tenant home says how many catalogs are still being prepared, the log says `2.0 upgrade finished` when all are, and `epistola_catalog_upgrade_queued` counts those waiting. **Action on upgrade:** deploy these versions to every environment, which refuses document requests until you do; resubmit requests that failed in the queue; with the HPA on, scale the application back up after the upgrade.
