title: The upgrade from 1.x keeps what was published as a draft to release, and cuts or deploys nothing.
---

Upgrading from 1.x is a breaking upgrade that needs a maintenance window, and document generation stops at the upgrade until you release and deploy (follow the Upgrades guide). Before upgrading, stop every 1.x node (the migration does not check for one, and a 1.x node left running fails its requests until it is stopped, though it writes nothing), take a database-level backup and drain the generation queue, and plan to move REST clients to contract 2.0. On upgrade each authored catalog keeps what you were working on as its next draft, and gets beside it a draft **Published in 1.x** holding what each template and stencil last published (a template whose default variant was never published, and a stencil never published, are left out); where the two would be the same there is only the next draft. The upgrade cuts no release and runs nothing after startup: release "Published in 1.x" (or the next draft) yourself, numbered by default as the next patch after the catalog's latest 1.x release, or 1.0.0. 1.x declared no dependencies, so the upgrade declares, pinning nothing, every catalog a catalog's content uses; releasing pins each to that catalog's latest release, which the release dialog shows, and refuses, naming it, a catalog with no release yet. A catalog subscribed to from a URL receives its source's release at boot, retried at the next boot when its source cannot be reached. The 1.x template, data contract and stencil versions and the environment activations are removed once the upgrade has taken what it needs; a summary of them (version numbers, statuses, dates, and what each environment had activated) is kept as the `upgrade-1x-history` record in `app_metadata`, and the content of older versions is not kept. The 1.x releases themselves are removed, since they kept only a number, a fingerprint and notes, and their Exchange publication records with them. The tenant home lists the catalogs from 1.x that have no release yet. **Action on upgrade:** release each catalog's "Published in 1.x" draft (or its next draft) and deploy it to every environment, which refuses document requests until you do; resubmit requests that failed in the queue; with the HPA on, scale the application back up after the upgrade.
